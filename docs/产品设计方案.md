## 1. 背景与场景洞察

### 1.1 目标用户与核心痛点

| 用户画像 | 典型场景 | 现状痛点 |
| --- | --- | --- |
| 学生 / 考研求职者 | 开题前了解一个研究方向、面试前研究目标行业与公司 | 搜索结果碎片化，需翻 20+ 网页人工拼凑 |
| 初级职场人 | 领导临时布置的"下午给我一份 XX 的调研" | 整理耗时 2~4 小时，产出质量依赖个人经验 |
| 内容 / 咨询从业者 | 快速产出某主题的结构化综述初稿 | 直接问 AI 有幻觉且无来源，不敢直接引用 |

**核心痛点总结**：人工检索整理耗时、AI 对话产出不可溯源。

### 1.2 场景适配性判断（为什么用 Agent 做）

- ✅ **任务可分解**：研究天然是"拆问题 → 逐个检索 → 汇总撰写"的流程，适合规划-执行结构
- ✅ **需要工具**：模型自身没有实时信息，必须联网搜索与网页阅读（Function Calling）
- ✅ **结果可验证**：产出附来源链接，真实性可核验，幻觉风险可控可查
- ⚠️ **明确不适配**（写入 MVP 边界）：需要一手数据、专家访谈的深度咨询级研究；毫秒级响应场景

### 1.3 竞品参照与差异化

参照 Perplexity Deep Research、Kimi 探索版等。差异点：**个人可私有部署、研究角度与报告模板可自定义、单次成本可压到几毛钱级**——定位是"自用的研究流水线"，而非通用问答产品。

## 2. 产品定位与 MVP 边界

**一句话定位**：输入一个研究主题，Agent 自主完成"规划 → 联网检索 → 阅读 → 撰写 → 自检"，交付一份带参考来源的结构化研究报告。

### 2.1 MVP 做什么 / 不做什么

| MVP（v1.0）做 | v1.0 不做（后续版本再说） |
| --- | --- |
| 单主题输入 → 自动生成 md 报告 | 多用户、账号体系、付费 |
| 3~5 个子问题自动拆解与检索 | 定时任务、订阅式日报 |
| 报告强制附参考来源链接 | PPT/网页等多格式导出 |
| 生成失败的分级兜底 | 多语言报告（仅中文） |
| Streamlit 网页界面 + 进度可视化 | 移动端 |

### 2.2 成功标准（量化）

| 维度 | 指标 | 目标值 |
| --- | --- | --- |
| 质量 | 来源真实率（引用链接可打开且内容相关） | ≥ 95% |
| 质量 | 报告可用率（盲评 5 分制 ≥ 4 分） | ≥ 70% |
| 体验 | 单份报告端到端时长 | ≤ 8 分钟 |
| 成本 | 单份报告模型调用成本 | ≤ ¥0.5 |

## 3. 用户流程与交互形态设计

### 3.1 主流程

```text
┌─────────┐   ┌──────────┐   ┌──────────────┐   ┌──────────┐   ┌─────────────┐
│ 主题输入 │ → │ 任务规划  │ → │ 自主检索研究   │ → │ 撰写与自检 │ → │  结果交付    │
│         │   │ (可见可干预)│   │ (进度实时反馈) │   │          │   │ (报告+来源)  │
└─────────┘   └──────────┘   └──────────────┘   └──────────┘   └─────────────┘
                      ↓任意环节失败 ↓                              ↓
                 分级兜底（见第 7 节）                        追问 / 局部重写
```

### 3.2 各阶段交互定义

**① 主题输入**
- 输入框 + 三个可选参数：研究深度（快速/标准/深入，影响子问题数与检索轮次）、报告篇幅（1~3 千字）、关注角度（自由文本，如"侧重技术路线"）
- 输入校验：空输入、超长输入、敏感词的即时提示（L0 兜底）

**② 任务规划（可干预性是信任来源）**
- 展示 planner 拆解出的 3~5 个子问题清单，用户可：直接开始 / 增删改子问题后再开始
- 设计理由：研究类任务用户最关心"方向对不对"，前置干预比事后重跑省成本

**③ 进度反馈（长任务的核心体验）**
- 阶段级状态：`正在检索子问题 2/4：XX` + 当前工具调用（搜索词 / 正在阅读的 URL）
- 工具调用轨迹可展开查看——既是进度反馈，也是"它真的在查资料"的信任设计
- 预计剩余时间提示（按已完成子问题耗时估算）

**④ 结果交付**
- 报告结构模板：摘要（150 字内）→ 核心要点（3~6 条，每条可附来源角标）→ 分节分析 → 结论与展望 → 参考来源列表（编号 + 标题 + URL）
- **硬性规则：任何事实性陈述必须有来源角标；无来源内容仅允许出现在"分析推论"段落并显式标注**
- 交互动作：下载 md / 复制全文 / 对某一节发起追问 / 对某一节重写 / 一键重新研究生成对照版

**⑤ 异常态展示**
- 检索某子问题连续失败：不中断整体，标记该节为"资料获取失败"，报告中如实标注
- 全局失败：明确告知失败环节与原因，给出来源已收集的部分素材 + 重试按钮（见 7.3）

## 4. 系统架构概览（产品视角）

四节点工作流 + 工具层，与简历描述一致；每个节点对用户可见的行为如下：

| 节点 | 职责 | 用户可见行为 |
| --- | --- | --- |
| Planner 规划 | 主题 → 子问题清单 + 检索词 | 阶段②的子问题清单 |
| Researcher 检索 | ReAct 循环调用搜索/阅读工具，收集素材并去重 | 阶段③的实时轨迹 |
| Writer 撰写 | 素材 → 结构化报告（含来源角标） | 阶段④的报告 |
| Reviewer 自检 | 核查引用真实性、要点与来源一致性；不合格打回重写 | 报告末尾"自检通过项"说明 |

工具层：`web_search(查询)`、`read_page(url)`（正文抽取 + 截断至 4K 字）、`write_report(文件名, 内容)`。记忆设计：保留系统指令 + 任务目标 + 素材摘要，历史工具调用滚动压缩（对应上下文工程实践）。

## 5. 模型选型与调用策略（效果 / 廞迟 / 成本权衡）

### 5.1 分层选型原则

**不同环节对模型能力的要求差异极大，统一用旗舰模型是浪费，统一用轻量模型是赌命。** 按环节要求分层：

| 环节 | 关键要求 | 模型档位 | 候选（国产优先） | 权衡理由 |
| --- | --- | --- | --- | --- |
| Planner | 拆解质量决定全局，推理要求高 | 旗舰 | DeepSeek-V3 / GLM 旗舰 / Qwen 旗舰 | 调用 1 次，成本占比小，值得花 |
| Researcher | 工具调用稳定 + 便宜（循环多次） | 中档 | GLM-4-Air / DeepSeek / Qwen-turbo 档 | 循环 10+ 次，是成本大头，用中档换 70% 成本下降 |
| read_page 压缩 | 快、便宜、摘要够用 | 轻量 | 同上中档或更轻 | 纯摘要任务，效果差距小 |
| Writer | 长文结构与中文表达 | 中档偏上 | DeepSeek-V3 / GLM | 写作质量用户直接感知，不能太弱 |
| Reviewer | 严谨、指令遵循 | 中档 | GLM / DeepSeek | 核查任务，指令遵循 > 创造力 |

> 具体型号与价格随市场变动，开发时以当期刊例价为准重新核算；选型逻辑不变。

### 5.2 单份报告 Token 预算（标准深度估算）

| 环节 | 输入 Token | 输出 Token | 说明 |
| --- | --- | --- | --- |
| Planner | 1.5K | 0.5K | 1 次 |
| Researcher | ~42K | ~3.6K | 4 子问题 × 4 轮 ReAct，每轮上下文 ~3.5K（网页截断控制） |
| Writer | ~8K | ~2.5K | 素材 + 模板进，报告出 |
| Reviewer | ~5K | ~0.5K | 报告 + 来源清单 |
| **合计** | **~57K** | **~7K** | 按国产中档价位约 ¥0.1~0.2/份，旗舰做 planner 也 ≤ ¥0.5 |

### 5.3 延迟策略

- 子问题检索**并行化**（asyncio 并发调用搜索工具），串行是延迟最大的浪费
- 撰写阶段**流式输出**，用户看到文字逐步生成，心理等待时间减半
- 整体定位为**异步任务**（分钟级），不做实时对话的假象；进度反馈替代转圈等待

---

## 6. 成本失控防线

- 单份报告 Token 硬顶（如 150K），超限中止并走部分交付
- ReAct 单子问题循环上限（如 6 轮），防死循环烧钱
- 相同 URL 结果缓存，重复主题命中缓存直接复用素材

## 7. 多级兜底方案

### 7.1 兜底分级

| 级别 | 故障场景 | 兜底动作 | 用户感知 |
| --- | --- | --- | --- |
| L0 | 输入异常（空/超长/敏感） | 前置校验 + 引导修正 | 即时提示，未开始计费 |
| L1 | 单个工具失败（搜索超时/网页 403） | 重试 2 次 → 切换搜索源（duckduckgo → Tavily → 博查）→ 跳过并标记 | 轨迹中显示"已跳过" |
| L2 | 模型调用失败（限流/超时） | 指数退避重试 → 降级到备选模型（同档位互换） | 进度条暂停后恢复 |
| L3 | Writer/Reviewer 环节失败 | 基于已收集素材交付"素材汇编版"（要点 + 来源，不含成文分析） | 明确告知是降级产出 |
| L4 | 全局失败（规划后无任何素材） | 终止计费点，告知原因，提供已消耗信息 + 一键重试 | 失败页 + 重试入口 |

### 7.2 幻觉兜底（与 L 级并行）

- Reviewer 核验：抽样打开来源 URL 比对要点相关性，不通过打回重写（上限 2 次）
- 产品规则：无来源不陈述；推论必须显式标注"以下为分析推论"

### 7.3 部分交付原则

**任何情况下，已完成的工作不浪费**：全局失败也返回已收集的素材清单与检索轨迹，用户可换工具手动继续。

## 8. 效果评估指标体系

| 类别 | 指标 | 定义 | 采集方式 |
| --- | --- | --- | --- |
| 质量 | 来源真实率 | 引用可打开且内容相关占比 | 评估集人工抽检 + reviewer 自动核 |
| 质量 | 报告可用率 | 盲评 ≥4/5 分的报告占比 | 评估集人工评分 |
| 质量 | 要点支撑率 | 有来源角标的要点 / 全部要点 | 自动统计 |
| 体验 | 端到端时长 / 完成率 | 提交到交付耗时；未触发 L4 占比 | 日志 |
| 工程 | 工具调用成功率 / 重试率 | 按 L1 统计 | 日志 |
| 成本 | 单份成本 / Token 消耗 | 实际 vs 预算 | 日志汇总 |

**评估集构建**：20 个测试主题（技术 / 行业 / 公司 / 学术各 5 个，含 2 个冷门主题测兜底），每个主题预登记"期望覆盖的关键信息点"，用于要点覆盖率的客观比对。

## 9. 风险与合规

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| 幻觉进入正式结论 | 高 | 来源角标硬规则 + reviewer 核验 + 推论显式标注 |
| 网页内容版权 | 中 | 仅私有研究用途，报告标注来源与抓取时间；不批量转存原文 |
| 内容安全 | 中 | 输入输出过敏感词校验；主题白名单收敛在研究类 |
| 成本失控 | 中 | 第 6 节三道防线 |
| 上游 API 变动 | 低 | 供应商抽象层，模型/搜索源可配置切换 |
